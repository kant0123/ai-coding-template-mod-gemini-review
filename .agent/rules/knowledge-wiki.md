# ナレッジ Wiki 運用規約 (`wiki/`)

## 基本理念

- **コードが正、Wiki が従**: 仕様や動作に乖離を見つけたら Wiki を直す。Wiki の記述に合わせてコードを変えてはならない（コードのバグなら Issue を立てる）。
- **現状の記録（生きたドキュメント）**: これから作るものの仕様は Issue 本文に置き、`wiki/` には「実装した結果どうなっているか」を記録する。

## 書くもの / 書かないもの

- **書く（コードを読んでも分からないこと）**:
  - なぜこの設計なのか、却下した代替案とその理由
  - 事故・障害の経緯と再発防止策
  - 暗黙の前提、踏むと壊れる落とし穴
  - エントリポイントのコード参照（`path/to/file.py:123 記号名()` 形式。記号名が主、行番号は補助）
  - 外部サービスの癖、環境固有の事情
- **書かない（コードを読めば分かること）**:
  - 関数シグネチャや API パラメータの網羅リスト
  - クラス構造やディレクトリツリーの機械的な写し
  - コードの丸ごとコピー（引用ではなくパス参照にする）

## 運用サイクル (Query / Ingest / Lint)

1. **Query (着手前)**:
   - コード探索前に `wiki/index.md` を読み、過去の経緯や落とし穴を把握する。
   - `index.md` 末尾の「未作成ページ」節を確認し、他セッションが予約済みのページ名と衝突しないようにする。
2. **Ingest (実装後)**:
   - 実装が固まったら、影響ページと `wiki/log.md` の更新を必ず同一 PR に同梱する。
   - 新規ページ作成時は YAML frontmatter（`type`, `summary`, `updated`, `related`）を正しく付与する。
   - ページ間リンクは `[[page-name]]` 記法を用い、双方向リンク（`related`）を維持する。
3. **Lint (健康診断)**:
   - コミット後、`node scripts/wiki-lint.js` を実行して大域的な整合性を機械検証する。
   - カタログの更新時は `--write-index` オプションを使用する。
