# スコープ外の問題を起票する

> **このファイルはテンプレートです。** `<...>` を実プロジェクトの値に置き換えて使う。
> Issue 連携を採用しないなら、このスキルごと削除してよい。
> Claude Code で使う場合は `.claude/skills/file-issue/SKILL.md` に置く。

**発見した時点で、その場で起票する。** チャットに書いただけでは記録に残らず、そのまま失われる。
今の作業は中断せず、起票してから続きに戻る。

## 1. 起票の対象か判断する

**対象** — 今の作業では直さないと決めたもの:

- 触っているファイル・周辺で見つけた、今の作業と無関係な不具合
- 動いてはいるが明らかに誤っている実装、壊れているテスト、失敗する既存の CI ジョブ
- コードと乖離した Wiki 記述の原因がコードの不具合であるもの(Wiki 側は今の作業で直す)
- 修正すると PR が肥大化する / レビュー単位が混ざるため切り出したい変更

**対象外** — 起票しないもの:

- 今の作業の一部として直したもの(PR の説明に書けば足りる)
- 数行で直せて今の変更に自然に含まれるもの
- 「気になる」程度の主観的な指摘、確証のない推測

## 2. 既存の Issue を探す

```bash
gh issue list --state open --search "<キーワード>"
```

同じ問題の open Issue があれば**重複起票せず、新事実をコメントで追記する**。
範囲が重なるが明らかに広い(狭い)なら、既存 Issue にコメントした上で別途起票し、
相互に番号で参照させる。

## 3. 何件に分けるか決める

**基本単位は「1 PR で閉じられる修正単位」。** 指摘の数と Issue の数は一致しない。
複数の指摘が同じ修正で片付くなら 1 件にまとめ、別々の修正になるなら分ける。

次のうち **1 つでも「いいえ」があるなら分ける。**

- **直す場所は同じか。** 同じファイルの同じ節・同じ関数への編集に収まるか。
- **まとめて直す必要があるか。** 片方だけ直しても意味があるなら、それは独立した Issue。
- **根本原因は同じか。** 症状が似ていても原因が別なら別件(対処が別になるため)。
- **タイトルが一文で書けるか。** 「〜と〜」の並列になるなら分割のサイン。

- **粗すぎる** — クローズ条件が一文で書けない。「CLAUDE.md を見直す」「エラー処理を改善する」は
  着手点が無く、いつ閉じてよいかも決まらない。
- **細かすぎる** — その 1 件のために PR を作るのが割に合わない。誤字・節番号のような些細な指摘は
  関連する Issue に相乗りさせるか、対象外に倒して起票しない。

## 4. 起票する

```bash
gh issue create --label <bug|...> --title "<一文で症状>" --body "<本文>"
# Projects を使う場合のみ:
# gh project item-add <番号> --owner <owner> --url <作成された issue の URL>
```

本文には次を書く。**推測でなく、実際に確認した事実を書く。**

- 発見した経緯: どの作業中に(Issue / PR 番号)、どのファイルで(`path/to/file.py:123`)
- 症状と再現手順、期待する挙動
- 今の PR で直さない理由(一行)

秘匿情報(Webhook URL・トークン・鍵)は private リポジトリでも書かない。

## 5. 報告する

その作業の完了報告で Issue 番号を挙げる(例: 「作業中に別件を 1 件発見、#45 で起票」)。
1 件も無ければ、確認済みであること自体を述べる。
