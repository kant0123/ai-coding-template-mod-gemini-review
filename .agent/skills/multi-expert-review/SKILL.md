# 合議制専門家パネル — PR 前の監査

> **このファイルはテンプレートです。** 採用しない場合は `review/` ごと削除する。
> Claude Code で使う場合は `.claude/skills/multi-expert-review/SKILL.md` に置く。

仕組み全体の説明は [review/README.md](../../../review/README.md)。ここには手順だけ書く。

## 0. 2 段構えであることを最初に押さえる

| | 何をするか | 通ったときの意味 |
| --- | --- | --- |
| 段 1: 静的プレスキャナ | `review/panel_runner.py` が正規表現で定型パターンを検出 | **「問題なし」ではない。**足切りを抜けただけ |
| 段 2: エージェント側パネル | あなたが `review/prompts/` の 5 プロンプトを順に実行する | 監査済み |

**段 1 が APPROVE でも段 2 を省略しない。** プレスキャナは文脈を読まないので、
認可の抜けやドメイン不変条件の破綻は原理的に見えない。
逆に段 1 が Critical を出したら、段 2 に入る前にまずそれを潰す(自明な当たりなので速い)。

## 1. 監査対象の差分を切り出す

worktree の中で、`origin/main` からの差分をパッチにする。

```bash
git diff origin/main...HEAD > review/work/diff.patch
```

`...`(3 点)を使う。2 点 `..` だと main 側の他人のコミットまで差分に混ざり、
自分が書いていないコードを監査対象にしてしまう。

## 2. 段 1 — 静的プレスキャナを回す

```bash
python review/panel_runner.py --diff review/work/diff.patch --domain <domain> --task-id pr-local
```

`<domain>` はプロジェクトの既定(`general` / `fintech` / `distributed` / `healthcare` /
`embedded`)。触った領域が既定と違うなら、その領域のドメインを指定する
(決済まわりを触ったなら `fintech` 等)。

出力された `review/work/pr-local/final_consensus_review.md` を読む。

検査するのは `.py` `.c` `.h` `.ts` `.js` `.sql` のみで、`review/` 配下は既定で除外される
(散文やパネル自身のプロンプトには検出したいパターンが説明として書いてあり、
含めると必ず誤検知になる)。`--exclude <glob>` で足せる。

**`読み込んだ文字数` が 0 のときは理由を読む。** 「ドキュメントのみの変更」なら正常。
「対象が空」なら差分の切り出しに失敗しているので、APPROVE を信用せずパスとブランチを
確認してやり直す。

## 3. 段 2 — 専門家パネルを実行する

`review/prompts/` の 5 ファイルを **01 → 05 の順に**自分で実行する。
各プロンプトはロール定義そのもので、差分を入力として読ませる。

| 順 | プロンプト | 見るもの |
| --- | --- | --- |
| 1 | `01_security_auth.md` | Timing Attack、IDOR・認可バイパス、機密情報のハードコード |
| 2 | `02_architecture_concurrency.md` | 責務分離、N+1 クエリ、ロック順序とデッドロック |
| 3 | `03_domain_adversarial.md` | ドメイン不変条件の破綻、敵対的な境界値入力 |
| 4 | `04_qa_breaking_guard.md` | 破壊的変更、無防備な NOT NULL、テスト隠蔽 |
| 5 | `05_lead_consensus_triage.md` | 1〜4 の指摘を合議・トリアージして 1 枚にまとめる |

ドメイン不変条件の具体は `review/configs/domain_invariants.json` にある。
3 番目のプロンプトを実行する前に、対象ドメインの `critical_rules` を読む。

**大きな差分(数十ファイル)なら、01〜04 をサブエージェントに並列で割り当ててよい。**
これは `CLAUDE.md` が言う「真に独立していて並列化できる大規模な作業」に当たる。
小さな差分では自分で 5 つ順に回すほうが速い。05 の合議は必ず自分でやる
(各ロールの生レポートを突き合わせる工程なので、分割すると意味が無い)。

### 指摘を書くときの 3 原則

1. **偽陽性を出さない。** 実害のないチェックリスト項目、文脈を無視した教科書的警告
   (インメモリ辞書に TLS を要求する類)は却下する。指摘には必ず
   「なぜ本番障害・インシデント・データ不整合に直結するのか」の機序を書く。
2. **心理的安全性。** 「なぜこんな実装をしたのか」「初歩的なミス」といった非難表現を使わない。
   「〜のリスクを防ぐため、このように改善することを提案します」と書く。
3. **外科手術的な修正コード。** 概念論で止めず、そのまま適用できるスニペットを添える。

## 4. 判定に従って動く

| 判定 | やること |
| --- | --- |
| 🚨 Critical あり | **push・PR 作成の前に直す。** 直したら段 1 からやり直す |
| ⚠️ Warning あり | 今の PR で直すか、直さないなら **Issue に起票する**(`CLAUDE.md`「スコープ外の問題を発見したとき」) |
| 💡 Nitpick のみ | 数行で直せて今の変更に自然に含まれるものだけ直す。残りは起票しない |
| ✅ APPROVE | `pr-finish` に戻って push する |

**Warning を「あとで」とチャットに書いて済ませない。** 記録に残らず失われる。
今の PR で直さないと決めたなら、その場で起票する。

## 5. PR 本文に結果を残す

`pr-finish` の PR 本文テンプレートに「レビューパネル」の節を足す。

```markdown
## レビューパネル

- ドメイン: `<domain>`
- 判定: <APPROVE / COMMENT / REQUEST_CHANGES>
- 対応: <Critical を N 件修正 / Warning を #45 に起票 / 指摘なし>
```

`review/work/` は `.gitignore` 対象なので、レポート本体はコミットされない。
**残す価値のある知見(なぜその設計が危ないのか、踏んだ落とし穴)は `wiki/` に還元する**
(`wiki-ingest` スキル)。レポートそのものを wiki に貼らない — 生成物であり、
次の PR で作り直せるため。

## CI との関係

`.github/workflows/multi-expert-review.yml` が PR ごとに段 1 を自動実行し、
レポートを PR コメントに投稿する。Critical があればジョブが失敗する。

- **CI は段 1 しか回さない。** 段 2 はあなたの仕事で、CI は肩代わりしない。
- ローカルで段 1 を回しておくのは、CI の失敗を待たずに潰すため。
- 誤検知で落ちた場合は `review:skip` ラベルを付けて外し、**なぜ誤検知なのかを PR 本文に書く**
  (書かないと、次に同じパターンを見た人が判断できない)。
