# Wiki への Ingest

> **このファイルはテンプレートです。** `<...>` を実プロジェクトの値に置き換えて使う。
> Wiki を採用しないなら、このスキルごと削除してよい。
> Claude Code で使う場合は `.claude/skills/wiki-ingest/SKILL.md` に置く。

`wiki/` は**常に「今どうなっているか」を表す生きた成果物**で、書くのはエージェント、
読むのは人間。実装と同じ PR で更新しないと必ず腐るので、Ingest は PR の一部として行う
(別 PR に切り出さない)。

**コードが正、Wiki が従。** 乖離を見つけたら Wiki を直す。Wiki の記述に合わせるために
コードを変えない(コード側が不具合なら、それは別 Issue にする)。

ただし**直してよいのは、コード・テスト・ログと突き合わせて再導出できる乖離だけ**。
ページ間の散文的な矛盾(どちらが今の判断か解釈が要るもの)は勝手に統合せず、両論を残したまま
人間に判定を渡す。自分の判断で片方を消すと、消えた側の根拠ごと失われる。

## 何を書き、何を書かないか

ここが Wiki の価値を決める。**コードを読めば分かることを書くと、Wiki は陳腐化した複製になり、
読む価値もトークン効率も失う。**

**書く:**

- なぜこの設計なのか。検討して却下した代替案とその理由
- 事故・障害の経緯と再発防止策。実測値があれば数字ごと(「90 秒放置すると 3/3 失敗」)
- 暗黙の前提、踏むと壊れる落とし穴
- どこに何があるかの入口 — `path/to/file.py:123 記号名()` 形式で示す。**記号名が主、行番号は補助**
  (行番号だけだと編集のたびに黙ってずれる。lint は記号名の実在と行のズレを突き合わせる)
- 外部サービスの癖、本番環境固有の事情

**書かない:**

- 関数シグネチャや API パラメータの網羅リスト
- クラス構造・ディレクトリツリーの機械的な写し
- コードのコピー(引用ではなくパスで参照する)

## 手順

### 1. 影響するページを探す

```bash
cat wiki/index.md
```

`components/`(何が・どこに・どう繋がるか)、`concepts/`(なぜそうなっているか)、
`operations/`(どう動かす・壊れたらどうする)の 3 分類から、今回の変更が触る範囲を拾う。
典型的には 1 PR で 1〜5 ページ。

### 2. ページを更新する

- 新事実の追記、古くなった記述の書き換え、関連ページからの相互リンク。
- **`updated` を触った日に更新する。** `related` を直すだけの小さな変更でも必要
  (lint が最終コミット日と突き合わせる)。
- ページの位置づけが変わったら `summary` も直す。直したら index を再生成する。
- `related` は**双方向**にする。A の related に B を足したら、B の related にも A を足す。
- ページ間リンクは `[[page-name]]`。存在しないページへのリンクを残してよい —
  「まだ書かれていないページ」の印になる。ただしその場合は `index.md` の
  「未作成ページ」節に `- [[まだ無いページ]] — [[参照元]] から参照されている` の形で控える
  (控えの無いリンク切れは単なる書き損じと区別できないため、lint はこの規約で判定する)。

### 3. 新しいページが要るなら作る

新しい構成要素・概念が生まれたときだけ。**まず `index.md` の「未作成ページ」節に名前を控える
(予約)。** 他セッションが同じ概念を別名で立てるのを防ぐためで、実体を書き始める前に行う。
既に他セッションの予約が載っていたら、その名前に合わせる(重複したページを作らない)。

`wiki/<分類>/_template.md` をコピーして
`kebab-case.md` にする(**連番は付けない**。設計書と違い、ページに順序の意味はない)。

frontmatter は必須:

```yaml
---
type: component | concept | operation
summary: index.md のカタログに出る一行要約
updated: YYYY-MM-DD
related: [page-a, page-b]
---
```

`index.md` のカタログは `summary` から生成されるので、**index を手で編集しない**。

```bash
node scripts/wiki-lint.js --write-index
```

ページを追加・改名したときと、既存ページの `summary` を直したときに走らせる。
再生成を忘れると lint が食い違いとして落とす。

### 4. log.md に 1 件追記する

```markdown
## [YYYY-MM-DD] ingest | PR #123 <一行要約>
- 更新: [[page-a]], [[page-b]]
- 新規: [[page-c]]
```

種別は `ingest`(変更の反映)/ `query`(調査結果の還元)/ `lint`(健康診断)。
経緯や実測値など、ページ本体に収まらない背景は `- 備考:` として続けてよい。

**PR 番号は PR 作成後にしか分からない。** `pr-finish` の中で PR を作ってから
この行を埋め、追いコミットする。

### 5. lint で確認する

```bash
node scripts/wiki-lint.js       # package.json があれば npm run wiki:lint
```

**日付の判定は最終コミット日を見るので、コミットしてから走らせる。** 未コミットの状態で
走らせると `updated` が古いと言われる(git はまだ前のコミットしか知らないため)。

**注意(`注意:` で始まる行)はエラーではないが読む。** 特に「参照先が更新されている」は、
そのページの記述が古くなっていないかを確認する合図。確認して問題なければ何もしなくてよい
(直したなら `updated` を触った日に更新する)。

よく踏む指摘:

- `[[...]]` という**記法そのものを説明する**箇所はバッククォートで囲む(囲まないとリンク切れ扱い)
- 孤立ページ(どこからも参照されていない)は、関連ページから相互リンクを張って解消する

lint が見るのは大域的な一貫性だけ。矛盾するページ・コードと乖離した記述・
言及されるのにページが無い概念は、意味の理解が要るのでエージェント側の担当。

## Wiki を更新しないと判断した場合

タイポ修正など、Wiki に影響しない変更もある。その場合も**判断そのものは省略しない** —
PR 本文の `## Wiki` 節に理由を一行書く。

`.claude/hooks/check_wiki_updated.sh` を有効にしている場合、`gh pr create` は
`wiki/` の差分ゼロをブロックするので、コマンド先頭に `WIKI_SKIP=1` を付けて再実行する。

## Wiki に書くもの / Issue に書くもの

| 内容 | 置き場所 |
| --- | --- |
| これから作る機能の仕様・受け入れ基準 | GitHub Issue の本文 |
| 実装した結果どうなっているか | `wiki/` の該当ページ |
| いつ何をしたか | `wiki/log.md` と PR 履歴 |

**未実装の構想を `wiki/` に置かない。** 実装が入った時点で、現状として記述する。

## 調査結果の還元

調べて分かった価値ある知見(原因分析・比較・実測)は、チャットに流したまま消さず
Wiki のページとして残す。**この還元は事前承認済み** — 残す価値があると判断したら
「残しますか?」と聞かずに Issue 起票 → worktree → PR → マージまで進めてよい。
確認を挟むと、判断できているのに人間の一言待ちで知見が消えるため。
価値があるかどうかが微妙なときは、聞かずに「残さない」側に倒す。
