# ナレッジ Wiki 運用ガイド

このドキュメントは `wiki/` の**背景と導入手順を人間が読むためのもの**。
エージェント向けの実行ルールは [CLAUDE.md](../CLAUDE.md) の「ナレッジ Wiki」節にあり、
内容が食い違った場合は `CLAUDE.md` を正とする。

## なぜ設計書駆動から移行するのか

設計書駆動(`docs/design/NN_feature.md` を 1 本書いて 1 タスクとする方式)には
構造的な問題がある。

| 問題 | 内容 |
| --- | --- |
| 陳腐化 | 設計書は**実装前のスナップショット**。実装中に方針が変われば書いた瞬間から現実と乖離し、誰も直さない |
| 現状が読めない | 設計書が 40 本たまると「今どう動いているか」を知るには 40 本読んで差分を頭の中で合成するしかない |
| 知識の逃げ場が README | 設計書に収まらない知識(落とし穴・運用の癖・事故の経緯)が README や HANDOVER.md に流れ込み、数百行の塊になる |
| 検索効率 | エージェントは毎回コードを grep して同じことを再発見する。過去の判断理由はどこにも残っていない |

Wiki 方式はここを反転させる。ページは**現状を表す生きた文書**で、変更のたびに更新される。
実装前の仕様は Issue に置き、Wiki には実装後の現実だけを書く。

### 過度な期待をしないこと

- **ファイル数は減らない。** 設計書 40 本が Wiki 40 ページになるだけで、リポジトリは軽くならない。
  効くのは陳腐化の解消であって、ファイル数ではない。
- **トークンも自動では減らない。** 読むとき(`index.md` → 関連 2〜3 ページ)は減るが、
  書くとき(1 PR で数ページ更新)は増える。読む回数が書く回数を上回る開発では差し引きで得になる。
- **書きすぎると逆効果。** コードの写しを Wiki に置くと、陳腐化した複製が増えるだけで
  トークンも精度も悪化する。`CLAUDE.md` の「何を書き、何を書かないか」が最も重要な規約。

## 3 層

```
[生ソース]  コードベース / テスト / PR・Issue / 実行ログ / 外部ドキュメント
     │       ← Wiki からは読むだけ。変更は通常の開発ワークフローで
     ▼
[Wiki]      wiki/ 配下の md。エージェントが所有し、毎 PR で更新する
     │
     ▼
[スキーマ]  CLAUDE.md の「ナレッジ Wiki」節。ページ規約と役割分担の定義
     │       ← 実際に手を動かす順序は .agent/skills/wiki-ingest/SKILL.md
```

**コードが正、Wiki が従。** 乖離を見つけたら Wiki を直す。

## 開発フローとの接続

既存の worktree → PR → CI → マージの流れは変えない。**Wiki 更新を同じ PR に載せる**だけ。

```
[Issue 起票] ← 仕様・受け入れ基準はここに書く(設計書の代わり)
      │
      ▼
[worktree で実装] ── 着手前に wiki/index.md を読む (Query)
      │
      ▼
[Wiki 更新を同じブランチにコミット] (Ingest)
      │  git push → gh pr create
      ▼
[PR] ─────────► CI
      │  緑を確認して merge
      ▼
[main] ─────────► CD (オプション)
```

Wiki 更新を別 PR に切り出さないこと。実装と知識の反映がずれた瞬間から Wiki は腐り始める。

エージェントが実際に踏む手順(影響ページの特定 → `updated` の更新 → `log.md` 追記 →
wiki-lint)は [.agent/skills/wiki-ingest/SKILL.md](../.agent/skills/wiki-ingest/SKILL.md)
にある。`CLAUDE.md` 側にはページ規約と「何を書き、何を書かないか」だけを残してある。

## 既存プロジェクトへの導入手順

設計書がすでに数十本たまっているプロジェクトに後から入れる場合の手順。
**1 回の巨大な PR で全部やらない。** 骨組みだけ先に入れて、以後は機能 PR で肉付けする。

### ステップ 1: 骨組みを入れる (`chore/wiki-bootstrap` の 1 PR)

1. `wiki/` 一式と `CLAUDE.md` の「ナレッジ Wiki」節を追加する。
2. `wiki/overview.md` を書く。既存 README の「技術スタック」「データモデル」
   「ディレクトリ構成」あたりが素材になる。
3. 主要な構成要素 5〜10 個について `wiki/components/` にページを起こす。
   この時点では**入口となるファイルと責務だけ**でよい。落とし穴や経緯は後から足す。
4. `wiki/index.md` を埋め、`wiki/log.md` に最初の `ingest` エントリを書く。

### ステップ 2: 既存の設計書を仕分ける

`docs/design/` の各ファイルを 2 つに分ける。

| 状態 | 移し先 | 元ファイル |
| --- | --- | --- |
| 実装済み | 現状として `wiki/components/` `wiki/concepts/` に統合する | 削除 |
| 未実装・構想段階 | GitHub Issue に本文ごと転記する(ラベルで種別を付ける) | 削除 |

設計書を**削除することを恐れない**。git 履歴に残るので情報は失われず、
`git log -- docs/design/xx.md` でいつでも読み返せる。残しておくと「どれが現状か」が
分からなくなる方の害が大きい。

一度に全部やらず、**その設計書に関係する機能を次に触る PR で 1 本ずつ**片付けるのが安全。

### ステップ 3: README と HANDOVER を縮める

- `README.md` — 対外的な説明(何のプロジェクトか / セットアップ / 起動方法)だけ残す。
  内部知識(データモデルの経緯・注意事項・課題・実装済み機能一覧)は Wiki へ移す。
- `HANDOVER.md` — 引き継ぎ情報は `wiki/overview.md` と各ページに吸収し、削除する。
  「最後に何をしていたか」は `wiki/log.md` が担う。

### ステップ 4: `docs/design/` を削除する

仕分けが終わったらディレクトリごと削除し、`docs/design/README.md` への参照を
`CLAUDE.md` / `README.md` / hook 設定から取り除く。

## Lint(健康診断)

検査は**機械に任せる部分**と**エージェントに任せる部分**に分かれる。

エージェントは 1 ページ内で完結する局所ルール(frontmatter を書く、テンプレートに従う)は
よく守るが、**Wiki 全体にまたがる大域的な一貫性は自然には保てない**。壊れるのはいつも
後者側 — カタログの掲載漏れ、片方向になった相互リンク、実体を作ったのに残っている
「未作成ページ」の控え。ここは人間の目視でも見落とすので、機械に見張らせる。

### 機械: `node scripts/wiki-lint.js`

`package.json` があれば `scripts` に `"wiki:lint": "node scripts/wiki-lint.js"` を足して
`npm run wiki:lint` でもよい。外部依存は無い(Node 標準ライブラリのみ)。

- **リンク切れ** — `[[...]]` の参照先が存在しない。ただし `index.md` の「未作成ページ」節に
  控えてあれば意図的とみなして通す(控えの無いリンク切れだけを落とす)
- **控えの消し忘れ** — 「未作成ページ」に載っているのに実体ができているもの
- **孤立ページ** — `index.md` / `log.md` 以外のどこからもリンクされていないページ
- **`index.md` の掲載漏れ** — 実ファイルがあるのにカタログに無い
- **frontmatter** — 必須項目、`type` の値域、`type` と置き場所の一致
- **`updated` のズレ** — そのファイルの最終コミット日と一致しているか
- **`related` の片方向参照** — A が B を挙げているのに B が A を挙げていない
- **コード参照のズレ** — `path/to/file.py:123 記号名()` の参照先ファイルが存在するか、
  行番号が範囲内か、記号名がその行の近く(±5 行)にあるか。**行番号だけの参照は編集のたびに
  黙ってずれる**ので、記号名を主アンカーにする(記号名の無い参照は注意表示に留める)
- **陳腐化** — 参照している行が最後に変わった日(`git log -L`)がページの `updated` より新しいか。
  ファイル単位ではなく**行単位**で見る(無関係な編集で毎回警告が出ると読まれなくなる)。
  **注意止まりでエラーにしない** — 参照先が動いても記述が誤りとは限らず、機械には断定できない。
  ここで CI を赤くすると CI が「無視するもの」に変わる
- **index.md のカタログと `summary` の食い違い** — カタログは各ページの frontmatter の
  `summary` から生成する(`--write-index`)。手書きの一行要約はページ本文と別々に育ち、
  必ず片方が古くなるため

CI で回すなら `.github/workflows-optional/wiki-lint.yml` を `.github/workflows/` にコピーする。
**2 つ落とし穴がある。**

1. `updated` の判定は git の最終コミット日を見るので、**コミット前にローカルで走らせると
   古い日付で落ちる**。手元で確認するならコミットしてから。
2. CI では `fetch-depth: 0` が要る。既定の浅いクローンだと `git log` が空を返し、
   スクリプトは日付の検査を黙って飛ばす(= 通っているのに何も見ていない)。
3. **改行コードに依存する検査を足さない。** 作業ツリーの改行は `core.autocrlf` に左右され、
   Windows では CRLF になる。文字列を完全一致で突き合わせる検査は、正規化しないと
   **ローカルでだけ落ちて CI では緑**になる(index の生成領域の比較で実際に踏んだ)。

### エージェント: 意味の理解が要るもの

機械側が通っていることを前提に、月 1 回程度、以下を依頼する。

- **矛盾** — 別々のページが両立しないことを書いていないか。**扱いは 2 種類に分ける** —
  コードやログと突き合わせて再導出できる乖離は直してよいが、散文的な矛盾は勝手に統合せず、
  両論を残したまま人間に判定を渡す(エージェントの意味的判断が、後のセッションから事実として
  読まれてしまうため)。`index.md` の一行要約が
  ページの中身とずれていないかも含む(実際、ここが逆の意味になっていた例がある)
- **陳腐化** — コードと乖離した記述はないか(コードが正)。設定の既定値・関数名・
  ファイルパスを実物と突き合わせる
- **欠落** — 複数ページで言及されるのに自分のページを持たない概念

修正は 1 本の PR (`docs/wiki-lint-YYYY-MM`) にまとめてよい。新規ページの作成が要る指摘は
別 Issue に切り出すとレビュー単位が混ざらない。

## 閲覧環境

Wiki はただの Markdown なので特別なツールは要らないが、以下があると効く。

- **Obsidian** — Vault としてリポジトリを開くと `[[...]]` リンクを辿れる。
  グラフビューで孤立ページとハブが一目で分かる。
- **Dataview プラグイン** — frontmatter の `type` / `updated` で
  「30 日以上更新されていない component ページ」のような動的一覧を作れる。
- `grep "^## \[" wiki/log.md | tail -5` — 直近の動きを見る。
