# 繰り返し指摘される誤り

レビュー(agy レビュー)で**妥当と判定して直した指摘**を、誤りの種類ごとにまとめた台帳。
個々の指摘は PR コメントに残るが、そこは merge hook と経緯を追う人しか読まない。
ここに集めておかないと、次の実装者は同じ種類の誤りを別の場所でまた作る。

**読むタイミング:** 着手時(`worktree-start` 手順 1)と push 前(`pr-finish` の前提の確認)。
push 前は、自分の差分が下の各種類に当てはまらないかを 1 つずつ確かめる。

**書くタイミング:** 差し戻しの指摘を妥当と判定して直したとき(`agy-review` 手順 3)。
既存の種類に当てはまれば実例を 1 行足し、無ければ種類を足す。

## 書き方

- **単位は種類であって個々の指摘ではない。** 「`foo()` の空文字列を見ていなかった」ではなく
  「外部コマンドの出力が空・想定外の形のときを考えていない」と書く。事象ごとに書くと、
  次に別の関数で出る同じ誤りに当てはめられない。
- 各種類には「push 前に確かめること」を書く。自分の差分に対して答えられる問いの形にする。
- 実例は `PR 番号 — 場所 — 一行` で。修正コミットや PR を辿れれば詳細はそこにある(本文を貼らない)。
- 種類の数は増やしすぎない。似た種類が並んだら統合する。

誤検知(`false-positive`)と見逃し(`false-negative`)はここではなく上流の Issue に送る
(`review/README.md` の「記録の置き場所」)。ここはレビュー役ではなく**実装側の誤り**の記録。

> 初期の実例はこのテンプレート自身(`review/agy_review.py`)の開発で出たもの。
> 他プロジェクトに導入したら実例は消してよいが、種類はそのまま当てはまることが多い。

## 種類

### 外部コマンド・外部出力の異常系を考えていない

外部コマンド(`gh` / `git` / LLM CLI)やファイルシステムが返すものを、正常系の形のまま信じている。
空出力・非ゼロ終了・前置き付きの出力・エスケープされた値・OS で不正な文字を含む値で壊れる。

push 前に確かめること:

- 外部コマンドが失敗したとき・出力が空のとき、処理は止まるか。黙って成功扱いに倒れていないか
- 出力を解釈する正規表現・パーサは、引用符・空白・非 ASCII・前置きの付いた値でも合うか
- 外部から来たパスを `resolve()` / `open()` する前に、不正な値で例外が出たときの扱いがあるか
- 同じ記録(PR コメント等)が何度も書かれうるとき、どれを正とするか(最新か・全部か)を決めているか

実例:

- PR #8 — `review/agy_review.py ci_state()` — `gh pr checks` が失敗して出力が空のときに緑と判定していた
- PR #8 — `review/agy_review.py` JSON 抽出 — LLM 出力に前置きがあると JSON を取り出せない
- PR #20 — `review/agy_review.py` 差分パスの抽出 — 空白・非 ASCII を含むパスは `git diff` が引用符で囲むため正規表現に合わない
- PR #20 — `review/agy_review.py` パスの解決 — Windows で不正な文字を含むパスで `OSError`
- PR #33 — `review/agy_review.py has_unverified_critical()` — 評価の理由文に「未確認」があるだけで判定語と取り違えていた
- PR #33 — `review/agy_review.py has_unverified_critical()` — 過去の評価も見ていて、記録し直しても差し止めが解けなかった

### 新しく足した分岐・関数にテストが無い

既存の純粋関数のテストはあるが、今回足した分岐(再試行・エラー経路・オプションの付与)には無い。
レビューで指摘されてから足すことが繰り返されている。

push 前に確かめること:

- 差分で足した `if` / `except` / 引数の付け足しのそれぞれに、そこを通るテストがあるか
- 外部プロセスを呼ぶ関数は、呼び出しをモックして「何を渡したか」を assert しているか

実例:

- PR #8 — `review/agy_review.py` — `cmd_review` / `cmd_triage` / `cmd_check` / `call_agy` / `ci_state` にテストが無かった
- PR #23 — `review/agy_review.py call_agy()` — 再試行時の `--conversation` 付与にテストが無かった

### ルールを足したのに、同じ流れを書いた他の箇所と食い違う

ルールを 1 か所(スキルの表・CLAUDE.md)に足し、同じ流れを別に書いている箇所
(手順の見出しと結び・フローチャート・他スキルのテンプレート・hook の判定)を直していない。
読む場所によって逆の指示が出る。機械で見張れるルールを文書にしか書かないのも同じ誤り。

push 前に確かめること:

- 足したルールのキーワードで `grep` して、同じ流れを書いた箇所(見出し・図・テンプレート)がすべて整合しているか
- そのルールは hook / CI で判定できる形か。できるなら判定を足したか

実例:

- PR #33 — `.agent/skills/agy-review/SKILL.md` 手順 4 — 「CRITICAL が未確認ならマージしない」を足したが、手順 4 の見出しと結びは未確認でも無条件にマージさせていた
- PR #33 — `review/agy_review.py check_merge()` — 同じルールを hook が判定していなかった
- PR #33 — `.agent/skills/pr-finish/SKILL.md` — PR 本文テンプレートに「未確認」の起票が無かった

### 主目的のページ以外に触った Wiki の付随更新を漏らす

新しいページを書くことに気を取られ、リンクを張るためだけに触った既存ページの `updated`、
`log.md` の「更新:」行を漏らす。`wiki-lint` はテンプレートのプレースホルダーのような
一部のケースを注意止まりにするので、lint が通っても漏れは残る。

push 前に確かめること:

- `git diff --stat origin/main -- wiki/` に出る各ページの `updated` を今日にしたか
- 同じ一覧のページが、`log.md` のエントリの「更新:」「新規:」にすべて載っているか

実例:

- PR #34 — `wiki/overview.md` — リンクを足したが `updated` をプレースホルダーのまま残し、log の「更新:」にも載せなかった

### 再試行・再実行で前回の成果物を上書きする

同じ処理を 2 回目に走らせたとき、1 回目の出力やログを同じパスに書いて消している。
失敗の調査に要る記録が、再試行が走った瞬間に失われる。

push 前に確かめること:

- 再試行・ループの中でファイルに書くなら、2 回目は追記か別名になっているか

実例:

- PR #23 — `review/agy_review.py` — 再試行で `agy_raw_output.txt` を上書きしていた
